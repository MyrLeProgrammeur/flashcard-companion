# CLAUDE.md — `flashcard-companion` project

Native Android app (Kotlin + Compose) that replaces AnkiDroid as the review
client for the decks generated by the sibling project `flashcard-pipeline`,
with an AI explanation button grounded in the source PDF. See `README.md`.

## Context to load before acting

- The app is **standalone**. There is no backend to start, and nothing in
  `android/` may depend on one. `backend/` is decommissioned dead code: the
  server, its boot script and its two notification jobs were removed from the
  phone on 2026-09-17.
- The stable GUID `sha1(subject\x1ftheme\x1fquestion)` (see the pipeline's
  `db_writer.py`) is the join key — never `notes.id`.

## Rules

- **Nothing loads over the network at render time.** KaTeX and pdf.js are
  bundled in `assets/`. The single outbound request in the whole app is the
  Infercom call behind the AI features.
- The Infercom key lives only in the app's private SharedPreferences on the
  phone — never committed, never in `BuildConfig`, never on the PC.
- The synced folders (`.apkg` decks, course PDFs) are **read-only** to the app.
  All state goes in the app's own `companion_state.db`, so the app can never
  create a Syncthing conflict.
- `data/Store.kt`'s schema is deliberately identical to the legacy backend's
  `srs_store.py`, so a backend database can be imported wholesale. Do not
  "tidy" the column names.
- Porting scheduler logic: Python's `round()` is round-half-to-**even** and
  `difflib.ratio()` is Ratcliff/Obershelp, not Levenshtein. `SchedulerParityTest`
  is generated from the real Python output and guards both — regenerate it with
  `tools/gen_srs_tests.py` (needs `backend/` present) rather than editing
  expectations by hand.
- `ui/Strings.kt`, `ai/Prompts.kt` and `SchedulerParityTest.kt` were **generated**
  from the backend (generators in `tools/`). They are committed, so the app
  builds without it. Native-only
  strings go in `StringsExtra.kt`; wording that must diverge from the web app
  goes in its `overrideFr`/`overrideEn` maps, which win over the generated table.
- PDF↔card matching = MVP heuristic (see `SourceMatcher.kt`) — not guaranteed,
  with an explicit, visible fallback to explaining from the card alone.
- **Never a `Co-Authored-By: Claude` trailer** — nowhere (commits, PR, artifacts).

## Workflow

- Build: `cd android && JAVA_HOME=<jdk17+> ANDROID_HOME=<sdk> gradle assembleDebug`.
  A full build takes a few minutes on the phone itself; it works.
- Tests: `gradle testDebugUnitTest` (pure JVM, no device needed).
- The phone is reachable over `adb` and root is available via `su`, so an APK can
  be built, installed and driven (`adb shell input tap`, `adb exec-out screencap`)
  without Matheo touching it. Granting `MANAGE_EXTERNAL_STORAGE` needs root
  (`su -c "appops set ... allow"`); plain `adb shell` lacks the permission.
- A WebView swallows touches: anything interactive drawn under one (the card
  faces) needs the tap forwarded from JS, see `MathView.kt`.
