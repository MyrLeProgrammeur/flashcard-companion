# flashcard-companion

Native Android app for reviewing the decks generated by
[`flashcard-pipeline`](../flashcard-pipeline), with an AI explanation button
grounded in the card's source PDF.

The app is **standalone**: no server, no Termux, nothing to start. It reads the
`.apkg` decks and course PDFs that Syncthing mirrors onto the phone, keeps its
own SRS state in a local SQLite database, and renders everything natively.

- `android/` — the app (Kotlin + Jetpack Compose).
- `backend/` — **legacy.** The FastAPI server + web UI the app used to wrap in a
  WebView. No longer required by the app; kept because it still runs on a PC for
  browsing the same decks. See [Legacy backend](#legacy-backend).

## How it works

**Data flow.** `flashcard-pipeline` (run on the PC) turns course PDFs into
flashcard decks and writes them as `.apkg` files. Syncthing mirrors two folders
onto the phone, which the app only ever **reads**:

- the generated `.apkg` decks (default `/storage/emulated/0/syncthing/Flashcards`)
- the source course PDFs (default `/storage/emulated/0/syncthing/Cours`)

Both paths are configurable in Settings. Reading them needs Android's *all files
access* permission, which the app asks for on first launch.

**Card identity.** Cards are keyed by the stable GUID the pipeline writes
(`sha1(subject\x1ftheme\x1fquestion)` in its `db_writer.py`), never by the
Anki-internal `notes.id`. That is what lets review history and scheduling
survive a deck being regenerated.

**Storage.** All app state — SRS scheduling, review log, folders, archive,
exam entries, cached explanations — lives in the app's private
`companion_state.db`. Nothing is ever written into the synced folders, so the
app cannot cause a Syncthing conflict.

**Review flow.** Decks are listed by folder/subject and reviewed with a minimal
SM-2 scheduler. The rating buttons (Again/Hard/Good/Easy) map to SM-2 quality
scores and to graduated intervals that are configurable in Settings. Unseen
cards carry the epoch as their due date, so they are always due and always sort
to the front of a session.

**Maths.** Card text is dense with LaTeX, and Compose has no maths typesetter.
Cards are therefore rendered by KaTeX, **bundled in the APK** (`assets/katex`) —
no network, no CDN, so a card renders identically with the radio off.

**PDFs.** Course PDFs are displayed with Android's own `PdfRenderer`. Text
extraction for the AI grounding uses pdf.js, likewise bundled in the APK.

**AI explanation.** Tapping "explain" on a card:
1. fuzzy-matches the card's deck path against filenames and folder names under
   the PDF folder (an MVP heuristic, not a guaranteed per-card link);
2. extracts text from any matched PDF and sends it as grounding;
3. falls back to explaining from the card's question/answer alone, and says so
   explicitly in the UI;
4. calls Infercom (DeepSeek) directly over HTTPS.

This is the app's **only** outbound request. Everything else works offline.

**Language.** French/English toggle in the menu, independent of the codebase's
own language (comments and docs are English).

## Setup

1. **Install the APK** (see [Building](#building)).
2. **Grant all-files access** when the app asks — it needs it to read the
   Syncthing folders.
3. **Set the folders** in Settings if yours differ from the defaults.
4. **Paste an Infercom API key** in Settings to enable the AI features. The key
   is stored in the app's private preferences and never leaves the device.
   Without it the app works fully; only the explanation button is disabled.
5. **Optional:** set the daily reminder hour in Settings. It fires a local
   notification when cards are still due — no server, no Google services.

Coming from the old WebView build? Settings offers a one-shot **import** of the
Termux backend's `companion_state.db`; the schema is identical, so the whole
review history and schedule carry over.

## Building

No Gradle wrapper is committed. Build with a JDK 17+ toolchain and an Android
SDK (compileSdk 35):

```bash
cd android
JAVA_HOME=<jdk> ANDROID_HOME=<sdk> gradle assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

`android/local.properties` (gitignored) must point `sdk.dir` at your SDK.
Installing over a build signed with a different debug key fails with
`INSTALL_FAILED_UPDATE_INCOMPATIBLE`; `adb uninstall com.matheo.flashcardcompanion`
first. That erases the app's database, so run the import above afterwards, or
keep a copy of `companion_state.db`.

Run the tests with `gradle testDebugUnitTest`. `SchedulerParityTest` is
generated from the Python backend's real output and checks the Kotlin scheduler
against it case by case — including Python's round-half-to-even and `difflib`'s
Ratcliff/Obershelp similarity, both of which a plausible-looking Kotlin
equivalent gets subtly wrong.

## Repo layout

```
android/app/src/main/java/com/matheo/flashcardcompanion/
  srs/Sm2.kt              SM-2 scheduler (pure functions)
  data/ApkgReader.kt      .apkg (zip + SQLite) parsing, Anki schema 11 and 18
  data/Store.kt           SQLite state; schema kept identical to the backend's
  data/Library.kt         deck tree, display-only folders, archive, due queue
  data/SourceMatcher.kt   deck <-> source PDF matching + difflib-compatible ratio
  data/Repository.kt      what the screens talk to, in place of the HTTP API
  ai/                     Infercom client, prompts, PDF text extraction
  ui/                     Compose screens, design tokens, FR/EN strings
  notify/DueReminder.kt   daily due-cards notification
  assets/katex, assets/pdfjs   bundled, offline
backend/                  legacy FastAPI server + web UI
docs/plans/               design history and open decisions
```

## Legacy backend

`backend/` is no longer used by the Android app. It still runs if you want the
web UI on a PC:

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env          # set INFERCOM_API_KEY
uvicorn main:app --reload --port 8420
```

Point `config.yaml`'s `paths.apkg_dir` / `paths.pdf_dir` at folders holding some
`.apkg`/PDF files. Tests: `pytest backend/tests/`.

Note that the backend and the app keep **separate** databases. Reviewing in both
means two diverging schedules.
